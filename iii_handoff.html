01 What Is iii

iii is an architectural bet. It is a backend orchestration system that attempts to unify ordinary backend services and AI agents under the same set of primitives — so that an agent is not an alien sidecar bolted onto your production stack, but simply another governed worker inside it.

The name "iii" refers to its three core primitives. Every entity in the system — whether a traditional microservice, a scheduled job, an ML pipeline, or an LLM-powered agent — speaks the same three-word language.

"iii is not the model. It is not the app. It is not the product strategy. It is the coordination substrate that exposes what the organization can do."

Input Intent / Unstructured Context docs, events, images, prose
Interpret Model (LLM) plan, transform, classify
Act Capability Registry (iii) functions · triggers · workers
Persist State write, read, handoff
Check Verifier / Approval Gate policy, test, human
Record Semantic Trace why · what · who approved
Primitive I
Function
A named unit of work with declared inputs, outputs, owner, risk level, and permission requirements. Examples: validate_order, issue_refund, summarize_document, request_human_approval.
Primitive II
Trigger
Something that causes work to start. Can be an HTTP request, a schedule, a queue message, a state change, a user action, a stream event, or a direct call. The same trigger model applies to cron jobs and agent handoffs alike.
Primitive III
Worker
Any process that connects to the fabric and registers capabilities. A TypeScript service is a worker. A Python ML pipeline is a worker. An LLM-powered agent is a worker. All governed by the same rules.
before · after — same workflow, two paradigms
// Before: a small product made of integration glue — two separate state machines
support_ticket_to_jira_app:
  poll support_api   // one loop
  parse ticket_thread   // guesswork
  call llm_classifier   // sidecar
  retry jira_api   // its own retry state
  log somewhere_else   // orphaned

// After: composition inside shared backend fabric — one state machine
trigger: support::ticket_created
functions:
  - support::read_thread
  - llm::classify_bug
  - jira::create_issue
  - human::review_if_uncertain
  - support::reply_with_link
state: ticket_to_jira_mapping
trace: one chain, visible end to end
02 Why It's Important

The problem iii solves is the two-state-machine problem. Today's agent demos have a private little loop — prompt, tool list, memory hack, retries, backend API calls, and logs somewhere else — and then the actual backend has its own APIs, queues, cron jobs, retries, state, and observability. These are two separate systems pretending to be one.

As agents become production actors — not demos but real processes that issue refunds, update records, deploy code, and send legal communications — this fragmentation becomes an operational liability. Without a unified fabric, every new agent workflow requires bespoke scaffolding, and every incident requires archaeology across disconnected logs.

iii's contribution is to collapse that gap: the agent's tools are backend functions; its memory is backend state; its handoffs are triggers; its execution is traced like everything else.

Why this matters at each layer of the stack:

Ops

Operational clarity. One observability model for agents and services means one set of dashboards, one incident runbook, and one source of truth for what happened.

Sec

Permission lattices. Every function call from an agent inherits the same authorization model as every other system call. There is no "agent bypass" of production controls.

Prod

Composability. A governed capability registry means new agents can discover and safely call existing capabilities without reimplementing integrations. Intelligence compounds on top of the fabric.

Risk

Blast radius control. Irreversible actions require declared approval gates. Budget limits. Tenant isolation. Prompt-injection boundaries. These are properties of the fabric, not per-agent hacks.

"The next moat is not a chatbot. It is a governed capability fabric: context, permissions, tools, verifiers, traces, and the right to act."

example · permission lattice for an agent worker
agent: refund_assistant
tenant_scope: current_customer_only
can_call:
  - orders::lookup
  - payments::calculate_refund
  - policy::check_refund_window
  - human::request_approval
can_call_with_approval:
  - payments::issue_refund  // if amount > $100
cannot_call:
  - users::export_all
  - admin::delete_account
  - payments::issue_refund_without_trace

"A universal capability fabric without a permission lattice is not architecture. It is an incident report waiting for a timestamp."

03 Alternatives, Products & Related Systems

iii names a category — agentic backend fabrics — not just a single product. The pressure is real regardless of which system wins. Below is the competitive map.

Tagged by role: DIRECT — same thesis   ORCHESTRATION — backend workflow   AGENT FRAMEWORK — LLM agent layer   INFRA — compute / primitives

Direct
Inngest
The likely origin of "iii." Durable functions-as-a-service with event-driven triggers, retries, and step-level observability. Designed to make background jobs and AI agents first-class equals in the same system.
→ Closest embodiment of the iii thesis
Orchestration
Temporal
Durable execution platform. Workflows written as code that survive failures, restarts, and long pauses. Strong in enterprise; increasingly used as the backbone for agent workflows that need ironclad durability guarantees.
→ More ops-heavy; stronger durability story
Direct
Trigger.dev
Open-source background jobs platform built around the same trigger → function → worker model. Explicit AI agent support; designed for TypeScript-first teams who want self-hosted capability fabric.
→ Open-source alternative; strong DX overlap
Orchestration
Prefect / Dagster
Data pipeline orchestration platforms. Handle observability, retries, scheduling, and dependency graphs for data workflows. Adding LLM steps; converging toward the agentic fabric use case from the data engineering side.
→ Strongest where data pipelines dominate
Orchestration
AWS Step Functions
Managed state machine orchestration from AWS. Integrates natively with Lambda, SQS, Bedrock, and hundreds of AWS services. High operational trust but low developer ergonomics and significant cloud lock-in.
→ Enterprise default; lowest DX ceiling
Agent Framework
LangGraph
Graph-based agent orchestration from LangChain. Models multi-step agent reasoning as stateful graph traversal. Focused on the model reasoning loop rather than full backend unification.
→ LLM-first; not a backend fabric replacement
Agent Framework
AutoGen / AG2
Microsoft Research's multi-agent framework. Emphasizes agent-to-agent conversation, specialized sub-agent roles, and human-in-the-loop handoffs. Strong research pedigree; maturing toward production use.
→ Multi-agent conversations; less backend depth
Agent Framework
CrewAI
Role-based multi-agent orchestration. Agents are assigned explicit personas, tools, and goals; they coordinate via defined workflows. Focused on task decomposition rather than backend fabric integration.
→ Ease of use; shallower infra story
Infra
Modal
Serverless compute for ML workloads. Functions deploy instantly with GPU access, secrets management, and scheduling built in. A substrate layer agents can run on; not an orchestration fabric itself.
→ Compute layer; pairs with orchestrators
Infra
Cloudflare (Workers + Queues + DO)
Durable Objects give stateful workers at the edge. Combined with Queues and Workers AI, Cloudflare is quietly building its own capability fabric — globally distributed, with tight permission primitives.
→ Edge-first architecture; different tradeoffs
Infra
Anthropic MCP
Model Context Protocol. An open standard for exposing tools and resources to LLM agents in a structured, permissioned way. Functions as the protocol layer that a capability fabric like iii could implement natively.
→ Protocol standard, not an orchestrator
Orchestration
n8n / Zapier / Make
Visual workflow automation tools. Adding AI nodes; widely adopted by non-engineers. Represent the low-code end of the capability fabric spectrum — strong breadth of integrations, weak in permissioning and audit depth.
→ Accessible but governance-shallow

"iii may win or not. The pressure is real either way: agents, workflow engines, APIs, queues, cron jobs, state stores, and observability cannot remain separate forever if agents become production actors."

04 What This Enables — Obvious Consequences

When semantic cognition connects to governed capabilities at scale, two futures become plausible simultaneously. The fabric itself is neutral; the order of deployment is not.

↑ Optimistic Case — Humane Leverage
Government forms and bureaucratic navigation become less adversarial — agents that understand intent can route, translate, and pre-fill.
Healthcare navigation becomes less cruel — agents that know policy, records, and appeals paths reduce the suffering tax on patients.
Small organizations get expert-grade operations — capability fabrics democratize what previously required expensive specialists.
Engineers inherit institutional memory instead of Slack archaeology — semantic traces become queryable organizational knowledge.
Compliance evidence stops being ritual theater — verifier chains produce audit trails automatically as a byproduct of correct operation.
Support teams catch incidents earlier — agents monitoring operations can detect anomalies before humans notice the symptom.
Trapped knowledge becomes useful action — documents, policies, contracts, and tacit procedures become executable.
↓ Dark Case — Bureaucratic Violence at Machine Speed
Automated denial — rejection decisions previously constrained by human bandwidth now scale without limit.
Worker surveillance — capability fabrics that monitor output can trivially monitor people; the infrastructure is identical.
Opaque scoring — agents that make hiring, credit, and housing decisions can produce outcomes with no legible reasoning chain.
Deskilling — workflows that remove judgment from humans may also remove the ability to exercise it when the system fails.
Centralized control — organizations that build large private capability registries accrue power that is difficult to contest.
"The agent decided" — used as a liability shield, removing accountability from every consequential outcome.
Efficient cruelty — every institution becomes faster at extracting rent, enforcing terms, and hiding the reason for decisions.
— Humane Constraints That Must Be Built In
Recourse
People affected by consequential decisions must have a path to challenge, correct, and understand them. The fabric must make this traceable, not optional.
Proportionality
Agent autonomy should shrink as stakes, irreversibility, and asymmetry of power increase. High-consequence actions require human approval gates — declared, not bolted on.
Dignity
Systems should reduce drudgery without reducing people to monitored components inside an optimization machine. Automate paperwork before automating judgment.
Accountability
The organization remains responsible. "The AI did it" should have no legal, moral, or operational force. The semantic trace is evidence, not an excuse.

"Anything that materially affects healthcare, employment, housing, credit, legal status, education access, public benefits, personal freedom, or essential services should require explanation, appeal, audit, and accountable human ownership."

05 Agenda — What To Do With This
01
Inventory capabilities, not just APIs
Map everything the organization can do: read a record, issue a refund, generate a report, deploy code, send email, request approval, escalate risk. For each, write the contract: inputs, outputs, owner, permissions, risks, examples, verifiers.
02
Build verifier-rich workflows before adding autonomy
Ask: what proves success? What catches failure? What is reversible? What needs human approval? What is the blast radius? What trace will exist six months later when someone asks why this happened?
03
Pick humane leverage points first
Automate drudgery, navigation, error detection, translation, paperwork, and memory before automating punishment, denial, surveillance, or coercion. The order matters because incentives will otherwise choose the cruel path first.
04
Fix backend hygiene — it is now an intelligence ceiling
Bad APIs, undocumented side effects, ambiguous ownership, inconsistent state, weak permissions, and missing logs were already expensive. In the agent era, they become direct ceilings on what intelligence can safely do on top of your systems.
05
Evaluate iii-category tools against your stack
Inngest, Temporal, Trigger.dev, and AWS Step Functions all embody the same pressure at different points on the spectrum. Pick based on: language fit, durability requirements, self-hosting preference, existing cloud commitments, and governance depth.
06
Treat accountability as a design constraint, not a review step
Institutions that cannot explain their own decisions should not give those decisions to agents. If you cannot audit a human decision today, an agent will make the same decision faster and at greater scale — with less recourse.

"The future of software is the reorganization of institutions around executable context, governed capabilities, and verifier-bounded agency. The winning systems will not be the ones that let agents do anything. They will be the ones that let agents do useful things inside strong boundaries."

"Prosperity comes from reducing coordination costs and converting trapped knowledge into useful action. The goal is not frictionless automation. It is humane leverage — removing needless friction while preserving judgment, dignity, and recourse where consequences are serious."

This handoff is derived from the Agent-Native Systems Colloquium (Spring 2026). iii is treated as an architectural bet, not a guaranteed standard. The argument is intentionally stronger than "AI features will be useful" and intentionally weaker than "LLMs replace software." All consequential deployments require careful attention to permissioning, verification, provenance, human recourse, and liability.
