Episode 01 — Edge Dispatch

The Instant Deploy Problem

Cloudflare just made it trivial to run AI-generated code at global scale. Three people sit down to figure out whether that's a breakthrough or a disaster.

March 24, 2026 ~24 min read AI Infrastructure · Edge Compute · Risk
Kai — Infrastructure architect, builds on Cloudflare daily
Mira — ML engineer, ships AI agents in production
Dev — Security & reliability lead, professional skeptic
Act I — The Primitive
Kai

Okay, so Cloudflare moved Dynamic Workers into open beta this morning. But important context: the experimental API actually shipped back in September 2025, tucked inside their Code Mode announcement. It's been quietly hardening for six months. Today is the "we're confident, come build on this" moment.

Mira

Can you back up and explain what it actually is for anyone who hasn't read the post?

Kai

Sure. Right now, a Cloudflare Worker is something you write, deploy through a pipeline, and it lives at a fixed endpoint. Dynamic Workers flip that. Your parent Worker can receive or generate code as a string, call one function, and Cloudflare spins up a brand new V8 isolate to run it. Same machine. Same thread, even. Milliseconds. When the request finishes, it's gone. No containers, no Docker, no build step.

Dev

So it's eval-as-a-service on the edge.

Kai

That's provocatively reductive but... not wrong. The critical difference is isolation. It's a full V8 isolate, the same security boundary that the entire Workers platform has been built on for eight years. And you control exactly which bindings it gets. You can hand it access to a KV store, a D1 database, an RPC stub to your own API, and nothing else. You can even set globalOutbound: null to kill all network access entirely. Or you can intercept every outbound HTTP request the code makes, inspect it, inject credentials, rewrite it, or block it.

Dev

Wait. The credential injection piece is interesting. You're saying the sandboxed code never sees the API keys?

Kai

Exactly. The agent code calls fetch("https://api.stripe.com/..."), and your parent worker intercepts it on the way out and adds the auth header. The dynamic worker never knows the secret. So even if a prompt injection attack tricks the model into trying to exfiltrate credentials, there are no credentials in the sandbox to exfiltrate.

the entire deployment, in one call
const worker = env.LOADER.load({
  compatibilityDate: "2026-03-01",
  mainModule: "agent.js",
  modules: { "agent.js": agentCode },
  env: { CHAT_ROOM: chatRoomRpcStub },
  globalOutbound: null // fully isolated, no network
});

await worker.getEntrypoint().myAgent(param);
Mira

The numbers are what make this a different category of thing. A few megabytes of memory. Startup in under five milliseconds. That's roughly 100x faster and 10 to 100x more memory-efficient than a container. On the same machine that received the request, so zero extra network latency. Across every one of Cloudflare's hundreds of locations worldwide. And $0.002 per unique worker per day, waived during beta.

Kai

And here's the thing most people miss: there are no limits on concurrent sandboxes or creation rate. Container-based sandbox providers all impose those limits. Cloudflare explicitly says: a million requests per second, each loading a separate Dynamic Worker, all running concurrently? No problem. It's the same tech that's powered their platform all along.

Dev

There's one big constraint, though.

Kai

JavaScript. Or TypeScript. The blog is very upfront about this. Technically Workers support Python and WebAssembly, but for small on-demand code snippets, JS loads and runs much faster. Cloudflare's argument is: we're not talking about humans here, we're talking about AI. LLMs are experts in every major language, and their training data in JavaScript is immense. JavaScript, by its nature on the web, was designed to be sandboxed. It's the correct language for the job.

Dev

That's a real constraint that people will either love or hate. But I'll admit: for the "AI writes disposable code" use case, it's the right call.

Act II — The AI Play
Mira

Let me explain why AI people should be paying close attention. The origin story here is Code Mode, which Cloudflare introduced last September. Their thesis is that agents should perform tasks not by making sequential tool calls, but by writing code that calls APIs. They've shown that converting an MCP server into a TypeScript API can cut token usage by 81%.

Dev

81%? Where does that come from?

Mira

The comparison between tool-call style and code-style agent execution. Right now, when you build an agent that needs to chain five APIs, do some math, hit Stripe, update a database... it does it through sequential tool calls. Each one is a round-trip. The model writes a JSON blob, the system executes it, sends the result back, the model reasons about the next step, writes another JSON blob. It's slow, expensive, and fragile. Every round-trip is another chance for the model to lose context or hallucinate a parameter.

Mira

Code Mode flips that. The model thinks once, writes a single coherent TypeScript function that does the entire workflow, you load it as a Dynamic Worker, it executes in one shot. Only the final output enters the context window, not every intermediate step. Fewer failure points, way lower latency, and the model reasons about the whole flow instead of myopically optimizing each step.

Kai

And here's the clever part about how they expose APIs to the agent. Instead of OpenAPI specs, which are incredibly verbose, they use TypeScript interfaces. The blog shows a side-by-side: a simple chat room API takes maybe 15 lines of TypeScript type definitions. The equivalent OpenAPI spec is 70+ lines of YAML. For an LLM, fewer tokens to understand the API means fewer tokens to generate the code, which means fewer things to get wrong.

what the agent writes (the whole workflow in one shot)
// The user asked for a summary of Alice's recent messages.
// I'll filter the history in code so I only read what's relevant.

let history = await env.CHAT_ROOM.getHistory(1000);
return history.filter(msg => msg.author == "alice");
Mira

The proof of concept is Cloudflare's own MCP server. It exposes the entire Cloudflare API through just two tools, search and execute, in under 1,000 tokens. The agent searches for the right API surface, writes code against typed interfaces, runs it in a Dynamic Worker. The alternative would be hundreds of individual tool definitions that no context window could hold.

"Dynamic Workers turn LLMs from advisors that suggest code into actors that deploy code. That's a phase change."

Kai

Zite is the production example everyone cites. They build an app platform where users interact through chat. The LLM writes TypeScript behind the scenes to build CRUD apps, connect to Stripe, Airtable, Google Calendar, and run backend logic. Every automation runs in its own Dynamic Worker with access to only the specific services that endpoint needs. Millions of execution requests daily. Their CTO said they benchmarked every platform and Dynamic Workers won on speed and library support.

Mira

Think about what this means for AI providers. Claude Code runs locally on your machine. But imagine a version where Claude writes a script and it's running on Cloudflare's edge instantly. Sandboxed. Accessible from any device. With controlled bindings so the code can only touch what you authorize. Artifacts that graduate from sandboxed demos to real, globally distributed apps with their own storage and API bindings.

Dev

If the code works.

Mira

...Right.

Act III — The Hallucination in the Room
Dev

So here's my problem with this entire discourse. Everyone's celebrating the infrastructure achievement. Millisecond cold starts. V8 isolates. Two tenths of a cent. Cool. Genuinely cool. But the killer use case, the one Cloudflare is pushing hardest, "AI writes code and we instantly run it," has a massive, screaming hole that the excitement is papering over.

Kai

Hallucination.

Dev

Not just hallucination. The entire spectrum of ways AI-generated code fails. Hallucinated APIs that don't exist. Wrong argument types. Logic that works for the happy path and explodes on edge cases. Subtle bugs, off-by-one errors in financial calculations, race conditions, code that looks perfectly reasonable, passes a casual review, and silently does the wrong thing. We've taken the most unreliable author in the history of software and given it a one-click button to deploy to hundreds of cities worldwide.

Mira

That's fair. But you're conflating two things. The question isn't whether AI-generated code is perfect. It's not. The question is whether the overall system is designed to handle that imperfection.

Dev

And my point is that the narrative doesn't emphasize that. The pitch, the excitement, the energy... it's all about the speed. "100x faster than containers!" Which is true. But speed is not correctness. We've made it 100x faster to deploy code that might be wrong.

Kai

Now hold on. To be fair to Cloudflare, they're not selling the gold here. They're selling the shovels. This is a gold rush, and Cloudflare is the guy on the side of the road with a wagon full of beautiful, well-made shovels. Their business model doesn't require the AI-generated code to be correct. They provide the execution primitive. Whether the code that runs on it is good or bad, they get paid the same $0.002 per worker per day. The correctness problem is explicitly someone else's to solve.

"Cloudflare is selling shovels in a gold rush. The shovels are excellent. But whether there's actually gold where you're digging? That's your problem."

Dev

And that's a perfectly rational business position! But it means the marketing and the reality have a gap. The word "securely" is doing a lot of heavy lifting. Cloudflare is conflating security isolation, the code can't escape the sandbox, with correctness, the code does what you intended. They solve the first problem. Nobody has reliably solved the second.

Mira

Okay, so let me push back, because there's a spectrum here. Not all Dynamic Worker use cases are the same. Zite isn't generating arbitrary programs. They're using constrained code generation: the model fills in templates, composes known API patterns, selects from pre-tested building blocks. The model writes against typed TypeScript interfaces, which means the failure surface is dramatically smaller than "write me any JavaScript you want." Those type definitions themselves act as guardrails: the model knows exactly what methods exist, what types they accept, what they return.

Dev

Agreed. And that's the only version of this that makes sense today. Constrained generation against typed interfaces. But that's not the vision the pitch is selling. The pitch is selling open-ended code generation deployed instantly. That's the exciting version. That's the version that doesn't work yet.

Act IV — The Middle Layer
Kai

So what does the responsible version look like? If I'm building on Dynamic Workers today, what should I actually do?

Dev

You need layers between the LLM and the load() call. And every layer you add erodes the "instant" promise, which is why nobody wants to talk about them.

Mira

Actually, Cloudflare is starting to talk about them. They've shipped helper libraries that are more interesting than most people realize. The @cloudflare/codemode SDK wraps the whole flow: it takes your tools, creates a purpose-built sandbox, and includes code normalization to handle common formatting errors from the model. It's a basic version of exactly the validation layer we're arguing is missing.

Dev

"Code normalization to handle common formatting errors" is a start. It's not a solution. That catches syntax issues, not logic bugs. Not hallucinated API calls. Not subtle data-corruption patterns.

Mira

Fair. But there's more. @cloudflare/worker-bundler resolves npm dependencies from the registry at runtime and bundles everything with esbuild. So the agent can import real, tested libraries instead of writing everything from scratch. Less hand-written code means less surface area for hallucination. And @cloudflare/shell gives the agent a virtual filesystem with transactional writes. If any write in a batch fails, earlier writes roll back automatically. That's a real guardrail against partial corruption from half-broken code.

Kai

The Code Mode SDK also has two server-side utilities worth knowing. codeMcpServer() wraps any existing MCP server, replacing its tool surface with a single code() tool. And openApiMcpServer() takes an OpenAPI spec and builds a complete MCP server with search and execute tools automatically. Both run the generated code inside Dynamic Workers with calls dispatched over RPC bindings. It's not just a raw load() call. There's real scaffolding here.

Mira

So let me synthesize the responsible stack. First: constrain the generation space. Use typed TypeScript interfaces. Give the model a narrow, well-defined API surface. The less creative freedom the model has, the fewer ways it can fail. The 81% token reduction isn't just about cost. Fewer tokens means fewer opportunities to be wrong.

Dev

Second: validate before deploying. Code Mode's normalization is step one. But you should also type-check, run against test cases, validate outputs against expected schemas. This is the boring, expensive step that makes everything actually work.

Kai

Third: control the blast radius. This is where Dynamic Workers genuinely help. The ephemeral nature is a feature. If a worker handles one request and dies, a bug is an error message, not a production outage. Use transactional writes from the shell library. Make things idempotent. Make them retriable. Lock down network access with globalOutbound. Use credential injection so the sandbox never holds secrets.

Mira

Fourth: human-in-the-loop for anything with side effects. If the Dynamic Worker is processing payments, modifying data, calling external APIs that change state... you need approval gates. The "AI deploys code instantly" story only works safely for read-only or idempotent operations.

Dev

Notice what we've described. We started with "one function call, instant deployment, milliseconds!" and ended up with "constrained generation, typed interfaces, code normalization, transactional writes, network lockdown, credential injection, human approval." That's not a criticism. That's the real product. The people who build that stack well will capture the value. The people who skip it will ship hallucinated code to production at global scale, very efficiently.

"The shovels are incredible. The question is whether you're digging in the right place. The validation layer is your map."

Act V — The Security Reality
Dev

I need to give Cloudflare more credit on the security side than I did initially. The blog has a dedicated section on this, and it's more serious than "V8 isolates are safe, trust us."

Kai

Yeah, this part matters. They auto-deploy V8 security patches to production within hours, faster than Chrome itself. They've built a custom second-layer sandbox on top of V8 isolates. They use hardware features like Memory Protection Keys. They've partnered with and hired leading researchers for novel Spectre defenses. They have systems that scan code for malicious patterns and automatically apply additional sandboxing layers. Nearly a decade of hardening against adversarial code.

Dev

That's a strong defense-in-depth story for security. I'll concede that. My skepticism was partially misplaced on that front. But it reinforces the distinction I keep making. All of this protects against the code breaking out. None of it protects against the code being wrong. You can have a perfectly sandboxed, completely secure worker that confidently charges someone's credit card the wrong amount because the model hallucinated the decimal place.

Mira

Two completely different threat models. The sandbox handles adversarial threats: prompt injection, code escape, credential exfiltration. Those are real and Cloudflare has real answers. The correctness problem, the model generating buggy or wrong code, is an AI reliability problem, not an infrastructure problem. And conflating them is dangerous because people hear "secure sandbox" and think "safe to use."

Dev

The novel adversarial surface I still worry about is the intersection of those two. What about an LLM that's been manipulated through prompt injection into generating code that looks benign, passes the normalization layer, but exfiltrates data through timing side channels? Or code that's technically correct but designed to rack up compute costs? The attack surface where "the AI is the vector" is genuinely new territory, even with eight years of experience securing against human-written malicious code.

Act VI — The Strategic Picture
Kai

Let's zoom out. What does Cloudflare want here? Because the pricing tells a story.

Mira

They want to be the default runtime for AI agents. And the shovel analogy is exactly right. In a gold rush, the people who reliably get rich aren't the miners. They're the ones selling picks, shovels, and denim. Cloudflare doesn't need the AI-generated code to be brilliant. They don't need the agents to be correct. They need everyone to try. Every experiment, every failed prototype, every hallucinated function that crashes on the first request... still pays $0.002 plus CPU time. The blog even says that cost is typically negligible compared to the inference costs to generate the code in the first place.

Kai

And if they become the default execution layer, they sit between every AI provider and every end user's infrastructure. Anthropic, OpenAI, Google, every agent framework, all deploying to Cloudflare. That's an enormously powerful position.

Dev

The blog hints at how deep this goes. Their own Cloudflare MCP server is built on Dynamic Workers. They're dogfooding this as the way to expose their own API. The entire Cloudflare API surface through two tools in under 1,000 tokens. If that pattern works, every major platform will want the same thing. And they'll all need a runtime.

Mira

For AI providers specifically, I see three things. One: agent execution backends. Claude Code, ChatGPT tool use, Gemini actions... all of them could adopt Dynamic Workers as their remote execution layer instead of maintaining their own sandboxing. Two: the platform-as-a-service pattern. Every developer who builds on an AI provider's API can now let their users inject custom logic. Webhooks, plugins, automation rules, all running at the edge, sandboxed, with controlled access. Three: the competitive pressure. "Write code and it runs instantly" is becoming the expected user experience. Any provider that can't offer it looks slow.

Dev

And the company that figures out the validation layer, the thing that sits between "model generated this code" and "this code is now live," that company has the actual defensible product. The runtime is becoming a commodity. Correctness is the moat.

Closing Thoughts
Kai

So where do we land? Because I don't think any of us are saying Dynamic Workers are bad. They're a genuine technical achievement and a real primitive that unlocks architectures that weren't possible before.

Mira

They remove the last big friction between "AI thinks of code" and "that code runs at global scale." The Code Mode paradigm, writing code instead of making tool calls, cuts token usage by 81% and produces better results. The typed TypeScript interfaces reduce hallucination surface. The helper libraries add real guardrails. This is going to change how agents are built. But the emphasis on "securely" needs an asterisk. Secure execution, yes. Correct outcomes... that's on us.

Dev

My one-liner: Cloudflare built the best shovels in the gold rush. They're fast. They're safe. They won't blow up in your hands. But they cannot tell you whether you're digging in the right place. The sandbox protects your infrastructure. It does not protect your users from wrong answers. And the danger is that the frictionless deployment makes it easy to forget that the correctness problem exists.

"The sandbox protects your infrastructure. It does not protect your users from wrong answers."

Kai

One more thing. This is one of those infrastructure moments that looks small today and reshapes what's buildable tomorrow. The people who win aren't the ones who deploy fastest. They're the ones who build the best guardrails around the speed. Typed interfaces. Validation pipelines. Transactional writes. Credential isolation. Human approval for side effects. That middle layer, between the model's output and the load() call, is where the real product lives. The shovel is amazing. Now go find the gold.
